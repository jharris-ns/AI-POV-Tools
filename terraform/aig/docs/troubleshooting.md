# Troubleshooting — Netskope AI Gateway Terraform Deployment

---

## The gateway is not showing as connected in Netskope

Allow up to **15 minutes** after the EC2 instance launches. Enrollment involves:
1. Instance boots and reads the Secrets Manager secret (~1–2 min)
2. Gateway process starts and contacts the Netskope cloud (~2–5 min)
3. Netskope marks the appliance as `connected`

**Check enrollment status via API:**
```bash
curl -s -H "Netskope-Api-Token: $NETSKOPE_API_KEY" \
  "$NETSKOPE_SERVER_URL/aig/appliances" \
  | jq '.elements[] | {name, status}'
```

**Check that the instance read the secret (confirms IAM and networking are working):**
```bash
aws cloudtrail lookup-events \
  --region YOUR_REGION \
  --lookup-attributes AttributeKey=EventName,AttributeValue=GetSecretValue \
  --query 'Events[*].{time:EventTime,resource:Resources[0].ResourceName}' \
  --output table
```
If the instance read the secret within 2 minutes of boot, the IAM setup is correct. If enrollment still hasn't completed, the issue is network connectivity from the gateway to Netskope cloud.

## The enrollment token expired

The token generated by `terraform apply` is valid for **24 hours**. If the instance has not enrolled in that window, run:

```bash
terraform apply
```

Terraform replaces the token resource, generates a fresh 24-hour token, and updates the Secrets Manager secret automatically. The instance reads the new token on its next boot.

## `terraform apply` fails with "resource limit exceeded"

```
Status 403: resource limit exceeded: license service is temporarily unavailable
```

This occurs when a previous appliance registration is still held in the Netskope tenant. Wait 30–60 seconds after a `terraform destroy` before running `terraform apply` again, to allow the Netskope license slot to free up.

---

## `terraform apply` fails with "state lock"

```
Error acquiring the state lock
```

A previous Terraform process was interrupted. To release the lock:

```bash
terraform force-unlock LOCK_ID
```

Replace `LOCK_ID` with the ID shown in the error message. If using a local state file and no other Terraform process is running, this is safe to force.

See [state management guide](state-management.md) for details on preventing lock conflicts with remote state.

## Instance launched but secret is not being read

Confirm:
1. **IAM** — the instance profile is attached (`test_instance_has_iam_profile`)
2. **DNS** — the VPC has `enable_dns_support = true` (required to resolve `secretsmanager.REGION.amazonaws.com`)
3. **Network route** — for `new-vpc-private`: NAT gateway must be deployed and the private subnet route table must point `0.0.0.0/0` to the NAT gateway
4. **Security group** — egress must allow all outbound traffic (`protocol = -1`)

---

## `terraform destroy` fails with access denied on a resource

The deployment IAM policy scopes permissions by `Name` tag (`aig-*`). If a resource's `Name` tag was manually removed or changed, destroy will be denied for that resource.

**Fix:** Manually restore the `Name: aig-*` tag in the AWS console, then re-run `terraform destroy`.

---

## AMI not found / InvalidAMIID

The AIG AMI is region-specific. Find the correct AMI ID for your region by subscribing to the Netskope AI Gateway on the AWS Marketplace — the AMI ID is displayed after you accept the subscription terms. Update `aig_ami_id` in your `terraform.tfvars` with the ID for your target region.

---

## `appliance_name` validation error

```
Error: appliance_name must be 1–15 characters (Netskope limit)
```

Netskope enforces a 15-character maximum on appliance names. Shorten your `appliance_name` value.

---

## The Netskope provider cannot authenticate

Ensure both environment variables are set **before** running `terraform`:

```bash
export NETSKOPE_SERVER_URL="https://mycompany.goskope.com/api/v2"
export NETSKOPE_API_KEY="your-v2-token"
```

`NETSKOPE_API_KEY` must be a REST API **v2** token (not an OAuth2 client secret). Generate it in your Netskope tenant under **Settings → Tools → REST API v2**.

## Checking the gateway logs via SSH

If you provided a `key_name` in your tfvars, you can SSH to the instance:

**new-vpc-public** (direct — instance has a public IP):
```bash
ssh -i ~/.ssh/your-key.pem ec2-user@$(terraform output -raw public_ip)
```

**new-vpc-private** (instance has no public IP — use SSM Session Manager instead):
```bash
aws ssm start-session --target $(terraform output -raw instance_id) --region YOUR_REGION
```

Or SSH via a bastion/jump host in the public subnet.

**existing-vpc:** depends on your network topology — check with your network team.
